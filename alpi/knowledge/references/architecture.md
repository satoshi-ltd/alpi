# Architecture answer pack

## Answer directly

- "Where is X implemented?" -> use the paths table.
- Desktop/mobile never read `~/.alpi/` directly; they call `host.*`.
- ALP is not the app API; ALP is peer-to-peer between alpi profiles. Host plane is client-to-daemon. Different sockets, different auth.
- alpi self-knowledge is native: `alpi_knowledge` reads `alpi/knowledge/references/`, not a skill.
- "Why is `alpi --version` fast / slow?" -> `cli.py` and `alpi.tui` never import `alpi.engine` or `litellm` at module level; only chat, `--once` and the TUI load them. A slow short command means a top-level import regressed (`tests/core/test_cli_cold_start.py`).

## Mental model

Local agent runtime, per turn:

1. Load profile config, memory, skill index, system prompt.
2. Run LLM turn with tool schemas.
3. Execute approved tools.
4. Persist session, logs, budget, events.
5. Optional daemon layer serves schedules, host clients, ALP.

## Engine contracts

- `Engine.run_turn()` owns one turn: append input, call model, execute tools, record usage, save session.
- `assistant_done` may be pre-tool narration or final output. Consumers delivering a canonical reply must filter `final=True`.
- Chat history lives in `sessions/`. New files use `schema_version: 2`: large user/assistant/reasoning/tool payloads are stored as bounded previews plus byte/hash metadata, not raw unbounded blobs. Scheduler/workgroup/system turns must not appear as ordinary profile chats.
- Client-facing reads go through `host.session.read`, which normalizes legacy and v2 payloads back to the shape clients render. Code that needs a durable review should use that path instead of assuming `tools[].args`, `tools[].result`, or `reasoning` are raw strings on disk.
- Session listings are bounded: large files are summarized from stat/head data, while `host.profile.summaries` uses `count_sessions()` / `latest_chat_summary()` so sidebar and Settings do not parse huge histories.
- Live reconnect replay uses `sessions/_events_<id>.jsonl`; incremental deltas are preserved exactly, while oversized text frames are clipped. The sidecar is reconnect/backfill, not the full durable archive, so do not treat it as the canonical session log.
- Each turn runs on a fresh Engine that rehydrates the session from disk (`_hydrate_from_path`). Cross-turn context = a resume note + each **replayable** prior turn — one that ended in a final reply, produced a file, or received a successful human `ask_user` answer; other aborted/tool-only turns are dropped so a resume never re-answers a dangling request. Each replayed turn contributes its user text (with an input marker `[attached: name (mime)]`) + assistant text (with a produced-file marker `[produced this turn … name → /abs/path]`). Successful human `ask_user` answers are replayed as user clarifications with their questions, before the assistant reply (4 KiB per answer, 8 KiB per turn; questions over 1 KiB and failed, fallback or clipped answers are excluded). They are redacted on save. Other tool calls and tool results are NOT replayed (context budget): an agent does not see its prior search/read/analyze output across turns — only its final text and the absolute paths of files it produced. A follow-up edit reuses the produced path from the marker, not a remembered tool result.
- Prompt-cache contract: `messages[0]` is the stable system prefix, tool schemas have canonical name order, and volatile clock/workgroup/skill/relay state rides each persisted user turn's `host_context` suffix so ordinary growth is append-only in every rehydrator. OpenRouter alone receives a hashed logical-conversation affinity; request-shape diagnostics persist bounded hashes only. Unsupported cache paths remain normal provider calls.
- A final assistant message with pending/in-progress todos is rejected; the model is re-prompted inside the same turn. The one exception is the max-steps wrap-up (below): it finalizes regardless of open todos, because no steps remain to re-prompt.
- Model iterations per turn are capped at `tools.max_steps_per_turn` (default 100) for every provider and budget. It bounds loops, refusals and the TODO guard, not cost. Hitting the cap does not discard work: normal chats get one tools-off best-effort wrap-up, while detached workgroup turns get one `workgroup_post`-only handoff.
- Compaction is checked before every model call of a turn, so a long tool loop compacts mid-turn: oversized tool outputs are truncated, tool outputs behind the kept tail are pruned to head and tail, and only then is the middle summarized by the fast tier; below that trigger the same prune also runs once the prompt passes `compaction.prune_after_tokens` (default 120,000 estimated tokens, `0` off) and frees at least 20,000 tokens, with no model call and the tail intact, so long tool loops on 1M windows stop re-sending old results; no summary is spent when the middle is only the previous summary, or is too small to matter while head and tail alone exceed the trigger. Each pass is a line in `logs/compaction.jsonl` (`trigger` auto, manual or prune) and an `auto_compact` event; the kept tail never opens on an orphan tool reply.
- Tool failures are keyed by tool, arguments and error text. The same call failing three times in a row injects one `[engine]` note asking for different arguments or another route; five identical failures exhaust that tool for the turn (refused without running). One tool failing three times in a row with the same non-empty error while its arguments change gets one note of its own and is never exhausted (`terminal` is exempt: its error is an exit status). Three consecutive failures with three different keys escalate once (effort `high`, else the `deep` tier), except that such a same-error run delays the escalation to its fifth failure; a mixed streak does neither. Every `[engine]` note injected into a turn is also written to the run journal as `agent.engine_note`, so `alpi runs show` tells how often a hint, nudge, time check or wrap-up fired. A tool's output is stored once in that journal, on `tool.finished`; the `agent.tool_end` after it holds `output_seq` instead, and `alpi runs show` / `host.run.read` return the text on both.
- An empty final reply closes a chat or scheduled turn when a delivery tool succeeded (`notify`, `email` send, `attach_file`) or the run is a silent scheduled job (`ALPI_SILENT_JOB=1`); a workgroup dispatch keeps its handoff nudge. Otherwise one re-prompt, with the effort escalation only in attended chat (never under cron or in a dispatch).
- One tool call is bounded by `tools.call_timeout_s` (default 600 s, `0` off), shortened to the turn's soft budget; a call past it returns a transient failure and the turn continues. `ask_user`, `peer`, `research`, `delegate`, `workflow`, `terminal` and `workgroup_post` are exempt.
- Host chat streams `usage` frames with accounting fields plus `context_tokens`. Only main-turn completions set `context_tokens`; side calls leave it at zero, so reconnect-capable clients can update the live context meter without confusing vision/research usage for conversation growth.

## Scheduler

- Agent jobs run via `alpi chat --once --emit-events --no-save`.
- Script jobs (`no_agent: true`) run directly, `shell=False`: `python3 [-u -B -I -E -s -O] <skill script>` or the skill script alone. Write the script as `${ALPI_HOME}/skills/<category>/<name>/scripts/<file>`: only an absolute path is accepted, and a relative one (`run.py`, `./run.py`) is refused from any folder, because a job runs from the daemon's folder and not from where it was created. The interpreter must resolve outside the profile home, the workspace and temp folders; a job that needs a pyenv, conda or uv environment kept inside the workspace must name an absolute interpreter outside those folders (else write `/usr/bin/python3`). The job's `PATH` drops empty, relative and agent-writable entries (profile home, workspace, temp, and `/private/var/folders` on macOS), so a bare `python3`, shebang scripts and their children resolve only outside them. A job left with no folder on its `PATH` is refused before it starts; move the workspace off a system folder.
- A fire that raises (the agent subprocess cannot start, a file is missing) is stamped `error` and reported like any failure; the rest of the pass still runs and the job is not re-fired every tick.
- Each fire is capped at `job.timeout` seconds (default 900, whole seconds from 30 to 86400; an invalid stored value fails the fire instead of being clamped; one profile's fires run serially) — a stuck-process backstop for unattended runs, not the cost guard (`budget.daily_usd` is) and not a hint that jobs must be short. Heavy jobs (deep research, multi-step publishing) raise it via `schedule(add|update, timeout=…)`. The scheduler hands the child a soft budget (`ALPI_TURN_BUDGET_S`, ~10% reserved) so the engine finalizes before the hard `subprocess` kill; the scheduled prompt states that budget in minutes, and the engine adds one `[engine] Time check` user note at 50% (time left only) and one at 80% (wrap up, do not start a step that may not complete), so the model can skip a long last step instead of being killed inside it (the soft deadline is only checked between steps); workgroup dispatch turns get the same notes, worded as "close the turn the way this task expects" so they never read as a request to post progress. Normal jobs return one tools-off reply; detached workgroup turns make one `workgroup_post`-only handoff. A run killed at the hard limit reports what it was doing — tool in flight and for how long, tool calls made, last message — in `schedule.failed`, the inbox row and the run ledger row, which also carries the `run_id` for every scheduled run.
- Provider pause: two consecutive account failures (`insufficient_credit`, `auth`, `model_unavailable`) pause a profile's agent jobs and workgroup dispatches for 15 min, two transport failures (`provider_unavailable`, `timeout`) for 5 min; the window doubles while failures continue (caps 4 h / 1 h, one probe per lapse with a 15 min slot if it never reports, one notification per pause) and the first success lifts it. Only the daemon process keeps the breaker; a TUI or CLI engine never opens one. Skipped jobs are not stamped, so they fire on the first tick after the pause; script jobs and chat are never paused. Opening files an error output and `schedule.failed` with `kind: provider`; lifting files an info output. `host.profile.summaries` carries `provider_pause` (`code`, `since`, `until`, `failures` or null); `alpi daemon status` prints it.
- `schedule.done` / `schedule.failed` payload: `profile`, `job_id`, `title`, `kind`, `message`, `reply`, `delivered_to`, `silent`. `schedule.failed` adds a plain one-line `body` ("reason; exit N; timeout: …", no markdown, safe for OS notifications and toasts), plus `output_id` + `deep_link` (`/outputs/<profile>/<id>`) for the persisted failure row, which is titled "<job> failed" and carries the markdown body (`**Reason:**` / `**Exit:**` / `**Timeout:**` + a fenced trace). `schedule.failed` is itself a client notification — failures are NOT re-emitted as `agent.message`.
- A job may carry a one-sentence `description` (160 characters at most; set it with `schedule(add|update, description=…)`, in English like the prompt) that clients show under its title. Run state keeps `last_run_message` (redacted failure, 300 characters) and `last_ok_at`.
- Jobs are silent by default (`notify: false`). Set `notify: true` and the reply is pushed to the owner's apps — the scheduler re-emits `agent.message` (`delivered_to="alpi"`) with `output_id` + `deep_link`. A job that wants to reach a THIRD PARTY uses the `email` tool in its prompt; that does not count as notifying the owner.
- In schedule subprocesses the parent daemon is the single source of truth: the child's `notify` is suppressed; the parent parses `tool_end` args to create the canonical output and re-emit `agent.message`. If the agent already notified itself, the scheduler skips the auto-notify (`delivered_to="external"`).

## Host API

Transport (see `deployments`):

- Unix socket `~/.alpi/host/host.sock` — local same-user clients, no token.
- WebSocket — paired remote clients reach the shared advertised address (`network.host`: Tailscale/LAN/VPN/hostname) with a per-device token.

Contracts:

- A `host.*` verb that takes a `profile` answers `-32004 not-found` for a profile with no directory and creates nothing; only `host.profile.create` makes one. Reading a profile's jobs never creates its `schedule/` folder.
- `host.events.subscribe` streams `{event, data, at, seq}`; `host.events.history` is `seq`-based (don't cursor on wall-clock).
- `host.events.*` is transport, not durable history. `host/events.jsonl` is a bounded reconnect replay buffer (`HISTORY_MAX = 500`) and may drop rows under load. Browseable history must query durable stores: outputs, sessions, workgroup transcripts.
- `host.chat.send` takes an optional `model` for the turn from an admin only; a member's override is answered with an `error` frame (`code: forbidden`) and the turn does not start. A member's turn runs on the profile's model.
- `host.chat.send` has a replay sidecar; recover missed frames via `host.chat.events_since(after_seq)`. A `tool_calls_pending` frame (once per span) says the model started a tool call: any text streamed since the last tool is a step of the work, not the answer. A local operator may launch the same lifecycle for an active paired connection with `alpi chat --once ... --connection-id <id>`; its local-only `host.chat.delegate` wrapper preserves connection ownership, `in_flight`, sidecar progress, and profile scope.
- `host.chat.send` streams a stable `run_id`. `host.runs.list` and `host.run.read` expose `runs/<run_id>.jsonl` journals made of bounded, redacted events (an unpaired surrogate in persisted text or in a frame sent to a client becomes U+FFFD) — start record, tool starts/states/ends, usage, model state, one `agent.reasoning_done {seconds}` per reasoning span, every `assistant_done` (only the one with `final=True` is the deliverable), errors and the finish outcome; streaming `reasoning_delta` / `assistant_delta` frames are never journaled, so a journal is an operational timeline, not a replay of the stream. Terminal command text is omitted from journals, saved turns and reconnect sidecars, `workflow` steps included (unstructured `steps` or step arguments are dropped from the record). `host.run.cancel` interrupts an owned active run, and the sovereign local socket may interrupt any active run. CLI/TUI equivalents are `alpi runs ...` and `/runs`.
- `host.chat.send` frames: `tool_start` carries `started_at` (epoch s), `tool_end` carries `duration_s` (1 decimal), and `reasoning_done {seconds}` closes each reasoning span when its deltas give way to a tool call, text or the step end; `seconds` is time spent reasoning (the first span of a step counts from that step's model call — the first step from the turn start, so it equals `reasoned_s` when that step streams no prose before its first tool; reasoning a retry or fallback discards is dropped from the span). All are stored in the replay sidecar as sent. Stored turns (`host.session.read`) carry the same spans as `reasoning_spans: [{seconds, before_tool, text?}]`, where `before_tool` indexes the turn's `tools` (the first call after the span; `len(tools)` before the answer) and `text` is that span's own reasoning (capped like a tool's reasoning, omitted when empty; `tools[].reasoning` stays the inter-tool prose and `reasoning` the joined trace for older clients); the field is omitted when a turn has no reasoning and on older sessions, which fall back to `reasoned_s`.
- A model-provider failure is one plain sentence, never the provider's exception text: `alpi/llm_errors.py` sorts the litellm exception chain into `context_length`, `insufficient_credit`, `auth`, `forbidden`, `model_unavailable`, `content_policy`, `rate_limited`, `timeout`, `provider_unavailable`, `bad_request` or `unknown`. The `host.chat.send` `error` frame carries `text` (the sentence) and `code` (the class; chat codes such as `busy` share the field); the redacted 500-character `detail` stays in the daemon log, the run journal, the TUI, `alpi --once` and a failed scheduled job's message, and never reaches ALP peers.
- The desktop and mobile apps put the daemon's protocol errors (`too-many-connections`, `too-many-requests`, `forbidden`, `method-not-found`, the close reasons `Authorization changed` and `Device authorization revoked`, transport failures) in plain words through one shared map, `common/plainError.mjs`; an unknown message is shown unchanged. Both apps retry a call or stream refused with `-32029 too-many-connections` once after 1.5 s.
- `host.profile.attention` (admin) lists what needs the owner in one profile: USER.md or MEMORY.md at 95 % of its limit or over it (listed until it drops under 90 %; AGENT.md has no enforced limit and is never listed), skills that fail lint or lack what they require, jobs whose last run failed, with `counts` and `total`; `attention.changed` says to refetch it. The daemon also files one `warning` notification the first time a memory file or skill is flagged, and `alpi profile show` and the TUI `/status` print the list.
- `host.activity.list` (no params) aggregates what needs the operator across profiles: `needs_you` (pending approvals/clarifications with `session_id`), `running` (`turn` rows for chat/delegate/peer/schedule/workgroup turns with `started_at` + `source`, and `workgroup` rows for running or between pipelines with `hub_id`, `phase` and `phases_done/phases_total`; a blocked pipeline is not listed) and `scheduled` (enabled jobs, soonest first, max 20, failed ones always kept, each with `status` (`scheduler.run.job_status`), `next_fire`, `last_run_at`, `last_run_status` and `last_ok_at`; admin-only, empty for members). Same filtering as the verbs it aggregates: owned sessions/prompts, profile scope. `activity.changed {profile}` (live-only, never in `host.events.history`; ≤ 1/s per profile) fires on turn start/end, prompt request/resolve, pipeline phase moves and `schedule.*`; clients refetch on it and on connect. `session_changed` carries `in_flight`; approval/clarification requests carry `session_id` (null when unknown). CLI: `alpi activity [--json]`; TUI: `/activity`.
- Desktop Schedule identifies running jobs by `(profile, job_id)`, shows elapsed time and disables another Run now; reopening restores canonical Activity. A job in Activity opens its schedule detail. A just-accepted request is shown briefly while activity arrives, and completion/failure clears that pending state.
- Questions and command approvals belong to the originating connection for every remote role, including admins: live `clarification.*` / `approval.*` events, replay history, pending lists, responses and activity all respect it. A remote admin shares prompts and running chat turns across devices of its own connection regardless of `session_scope`; member devices apply the device clause. Ownerless prompt events are hidden from remote clients. The local socket can handle prompts from all connections. This does not narrow other admin session reads or events.
- Under `session_scope: device` a remote member device sees only sessions of its own device (plus deviceless ones): `host.sessions.*`, `host.session.read`, `host.chat.*`, `host.runs.*`, `host.activity.list`, prompts, the profile summary, `session_search`, `session_read` and `recall_sessions` all apply it, and the events that carry session text (`session_changed`, `chat.turn_done`, `file_mutations`, `approval.*`, `clarification.*`) carry the owner and are dropped for other devices. `tests/host/test_device_scope_matrix.py` proves it path by path. Profile summary session counts follow host session ownership, including remote admins; workgroup posts and memory are profile-wide by design.
- `host.profile.summaries` = lightweight sidebar shape, carrying the profile's `accent` and `shape`, one of twelve names (round, squircle, drop, dome, pill, clover, cloud, bean, pebble, arch, heart, bell; a missing or unknown value reads as `round`) stored as `tui.shape`. The summaries send `shape` and never `fold`, and the apps read `shape` only. Input takes shape names only: `host.config.set_field` accepts `tui.shape` with one of the twelve names and answers `-32602 invalid-params` for anything else, an old origami id included, and for the old key `tui.fold` (set or unset). The only legacy handling is the daemon reading an old config that still stores `tui.fold`: it is translated on read (diamond round, shield bell, house arch, heart heart, plane drop, rocket pill, star clover, box squircle, bulb bean, tree pebble, crown dome, feather cloud; unknown → round, the default profile → twin; a `tui.shape` already set wins) and never rewritten by loading it; saving the shape writes `tui.shape` and drops `tui.fold`, keeping every other key. The apps draw the shape in the accent and name the pair by it ("blue bell"). The twelve colours are all hues (no grey); a new profile is seeded with the next pair of a fixed roulette, the least worn colour among existing profiles with its shape, so pairs only repeat once all twelve are worn; the retired grey `#7e8792` is reported as sky `#3ac9f3`. The default profile always reports `shape: "twin"` and no `accent` (clients draw Twin, alpi's robot-head mark, in the brand ink of the theme: `#14110c` light, `#f3efe6` dark, never an accent), and `host.config.set_field` refuses `tui.shape` and `tui.accent` for it. Every mark has two filled eyes (white on light, black on dark; one-ink icons, tray and favicon keep them cut out); the body is `markTone(accent, theme)` from `common/markTone.mjs`: the accent itself on dark, and on light a pale accent (amber, orange, rose, sky, teal, green, lime) deepened by the smallest OKLab lightness step until the white eyes reach 3:1, while the stored hex never changes and names keep `nameTone`; and one of eight states (idle, busy, working, needs, done, failed, paused, offline) with its own expressions and 3D turn, still under reduce motion. `busy` is only the loading indicator (Twin waiting), never a row: a row reads paused when the profile is paused, needs when it has no provider or a question or approval waits, failed after a recent failed job, working while a turn runs or a sent prompt waits for output, done for an unread reply, else idle. An unread profile also shows its name in bold; a workgroup row is never unread or bold: its place in the list and its time say what moved last. Paused profiles and workgroups draw a dashed neutral outline with no fill; on the phone only, every roster mark reads offline (faded, still) while the daemon is unreachable (the desktop banner owns the outage); such rows stay openable. In the desktop sidebar and the phone roster only the selected row animates; the others hold the still pose of their state and update live. Only the big hero mark of an empty desktop thread follows the pointer (never a paused one, never rows or the header); while it follows it faces front with no turn of its own, and the mouse wins over a focused composer until the next keystroke or a 2.6 s rest, when it looks back down at the composer; and every mark holds its still pose while the desktop window is unfocused or hidden or the phone app is in the background. The big empty-thread mark wears the session state, so a paused profile draws it paused. Under "Start a new thread" both apps show the profile's public bio (`public_bio`, sent as `bio`; three lines at most on desktop, five on the phone) and a Continue button into its latest chat session, titled by that session's first message (the user's own title for it on desktop), with its age; each is hidden when there is none, so a short bio written for workgroups doubles as the profile's introduction. The chat header mark is animated and follows the open session: working from send until the turn ends, needs while a question or permission request waits, failed when the turn ends in an error (until the next send), done for about 2.4 s after a successful turn then idle (a turn the user stops goes straight back to idle), paused when the profile is paused; moving to another session, profile or connection starts it from idle. The selected sidebar row and the selected phone row show that state merged with the roster: paused first, then a missing provider, then needs you, then the session state when not idle, then failed, working and unread. A workgroup wears a neutral soft honeycomb that lights up only when something happens, in the accent of the profile that owns the live phase (else the hub's): idle, done and queued are neutral (queued outlined), running fills only the current phase cell in that accent (finished cells faint, pending outlined), needs keeps the other cells solid neutral and draws the waiting cell in that accent, popped out above row size (header and larger; rows and inline marks fill it flat), failed fills that cell in the danger colour, paused is a dashed neutral outline and offline is faint; the lit colour is that accent toned for the theme ground like a name (`nameTone`), so pale accents still read; an owner that is not a profile on this device falls back to the hub's accent, and a hub that is not one either lights in the brand ink (Activity rows carry no owner and use the row's `hub_id`), and the owner of the phase is named in words ("Working · translate · @lingo", "Needs you · approval · @yuri"); `host.workgroups.list` with `include_pipeline_status` sends `pipeline_phase` for running, between and blocked pipelines, so a blocked row reads "Needs you · <phase> · @owner". A workgroup's title name (chat header, settings) is solid Bricolage in neutral ink, never the hub's tone; in rows it keeps the plain row type. A roster row reads needs you over failed (a job that failed in the last day) over working; a failed job running again (a running turn with its `job_id`) reads working. The default profile is listed first, and the desktop sidebar, the phone roster and the Fold draw it as the unlabelled first row above Pinned (dimmed when paused, never pinnable, never behind Show N more, ⌘1 on desktop); a member device that is not served the default profile simply has no such row. The desktop has no start screen: it opens on the first roster row's latest session (the default profile when served, otherwise the first profile row), and a new session starts from a profile's row menu or ⌘N. `host.profile.detail` = heavier settings shape; its payload field is `advertise_host` (not `tcp_host`).
- Profile settings in the apps save optimistically: a discrete choice (model, effort, tiers, vision model, shape, colour, budget, pause) shows at once everywhere the profile is drawn and rolls back with an error toast if the daemon refuses it; typed fields on the desktop debounce (about 600 ms) instead. Saves of one field reach the daemon in order, so it ends at the last choice; after a confirmed save the app keeps showing the choice until a fresh read lands, and when a newer choice fails over an older confirmed one it refreshes and shows what the daemon has. ## Tools

Each tool exposes `name`, `description`, JSON schema `parameters`, `run(...) -> ToolResult`.

Every turn binds one `RunContext`, `ToolExecutor`, and `ExecutionWorld`. Tools are exclusive by default; only an all-`parallel_safe` model batch can overlap, with results replayed in original order. A tool call whose arguments are not one JSON object never runs: it answers `arguments for <tool> are not valid JSON: …` (also for a key given two different values, nesting deeper than 100 levels, an unpaired surrogate or a number out of range such as `NaN`), `… are not a JSON object (got array)` or `… are missing (required: …)` with `; the call did not run.`, and the last call of a reply cut at `finish_reason=length` adds that the limit cut it off. Raw control characters inside strings are accepted, and the history sent back to the provider carries the decoded arguments (`{}` for a refused call). A top-level argument sent as a JSON string is decoded when its schema admits objects or arrays and not strings; `workflow` does the same for each step's own arguments, never for an expanded `${step.output}`. `tools.execution.backend` selects `local` or ephemeral `docker` terminal shell execution; Docker foreground containers are force-removed on timeout and background jobs are refused. Dedicated workers remain host-side, so this is not a whole-agent filesystem sandbox. The `workflow` tool runs a bounded dependency graph, shares `tools.max_parallel_tool_calls`, and routes every nested step back through `ToolExecutor`, so deny/member/availability policy cannot be bypassed.

- `write_file` / `edit_file` — syntax-lint before writing supported formats. Multi-document YAML (`---`, as in Spring `application.yml` and Kubernetes manifests) is accepted; each document is checked.
- `safe_write_secret(...)` — canonical path for credential files.
- `knowledge(action="search", query, k=5)` — semantic + lexical recall over synthesized Markdown pages in `<workspace>/knowledge/`; one bundle is indexed at a time and a `path` the index was not built for returns a hint, not another bundle's pages.
- `knowledge(action="ingest", source_path?|name?, topic?, ocr?)` — explicit learning from a source file or current-turn attachment. The source is read and summarized into Markdown; the raw file is not copied.
- `knowledge(action="maintain", source_path?, topic?, apply=true, ocr=false)` — explicit LLM-wiki workflow: write/update pages, update index/log, lint, then refresh the derived index.
- `knowledge(action="lint", path?)` / `knowledge(action="index", path?, force?)` — validate the bundle or rebuild the `okf_*` derived tables in `knowledge.sqlite`; indexing without a `path` also repairs the workspace bundle (required files, unlinked pages); a root given as an explicit `path` is never written to, indexing another bundle is refused without `force=true`, and the rebuild is a single transaction.
- `recall_sessions(query, k=5)` / `index_sessions(force?)` — semantic recall over past conversations. `session_search` stays the lexical first layer and `session_read` is the exact-browse layer (lists recent sessions or opens a windowed turn slice around a phrase/index, no model call); the semantic layer runs on the same embed/sqlite-vec store, separate `session_*` table family. Opt-in indexing (never automatic), active session excluded, no per-turn injection. Results follow the same ownership as `session_search`: a member sees its own connection, a device under `session_scope: device` only its own and deviceless sessions, admins everything. Forgettable: deleting a session purges its index rows (`recall.forget_session`), reindex orphan-sweeps gone sessions. Every index pass (incremental, `force`, embedder drift) is one write transaction; a failed pass leaves the previous index searchable. Legacy device-ownership backfills are reverified without rebuilding embeddings; unreadable owners stay unverified, never shared, and are retried on the next query. An unreadable session file aborts a destructive rebuild (`RebuildAborted`, old index kept); an incremental pass skips it.
- `workgroup_search(workgroup_id, query, k=5)` / `index_workgroups(workgroup_id?, force?)` — semantic search over hub-owned workgroup transcripts, same store, separate `workgroup_*` family. Hub-owned + profile-local only: no cross-peer/federated search. Decrypts via the existing key-history-aware path; opt-in, search scoped per-workgroup, no auto-injection. Forgettable: removing a workgroup (host RPC or CLI) purges its index (`workgroup_search.forget_workgroup`), reindex orphan-sweeps gone workgroups. Each pass (scoped or global `force`, embedder drift) is one write transaction; a failed pass leaves the previous rows searchable. A workgroup that fails to decrypt aborts a global `force`/drift rebuild (`RebuildAborted`, old index kept); incremental and scoped passes report it in `failed_workgroups`. ALP wire/crypto untouched.

## Attachments

- `host.chat.send` takes `attachments: [{path, mime?, name?}]`; the engine validates (magic bytes, binary-as-text guard, allowlist: images/PDF/text+source) and builds multimodal content-parts. Allowed text/source incl. `py`/`js`/`ts`/`tsx`/`go`/`rs`/`sh`/`sql`.
- Per-turn only: bytes live in the in-memory message. `session_metadata` is path-free (`{name, mime, size}`), but the engine re-adds a best-effort local `path` to each persisted chat-turn attachment so clients can thumbnail history — the path may be unfetchable cross-client (outside `fetch` roots) or after a staged file's TTL, so it's preview replay, not durable storage. Validated turn attachments also go to a runtime-only ContextVar (`tools/_state`) so tools resolve them.
- Remote clients upload via `host.attachments.stage` (caps + validation), getting a daemon-side path.
- Storage contract: synthesized Markdown lives in the **workspace** (`knowledge/`, source of truth); the derived SQLite index lives in the **profile** (`knowledge.sqlite`). Raw source documents used for ingest are not copied into alpi-managed durable storage.

## Daemon and env

- One daemon supervises every profile on the machine.
- Each profile's daemon tasks (schedule, alp, workgroups, workgroup-preempt; host on default) are supervised: a task that raises restarts after 5 s, doubling up to 5 min (a 5 min run resets the count); the 3rd failure in a row files one error output and `schedule.failed` with `kind: daemon`, and the next 5 min run files an info "recovered" output. `~/.alpi/service.tasks.json` holds each task's `state` (running|restarting|stopped), `failures`, `last_error` (redacted) and `retry_at`; `alpi daemon status --json` returns it as `tasks`.
- Profile `.env` loaded via `effective_profile_env`; the daemon does not mutate global `os.environ`.
- Before a profile's services start, the daemon binds legacy QA rewind counters/checklists to each workgroup's latest pipeline trigger and prunes workgroups without `meta.yaml`; a workgroup whose transcript cannot be read keeps its state and never holds the profile back (a trigger on it is refused). Trigger admission migrates the same way, also from the CLI with the daemon stopped.
- Hub baseline hashing and transcript writes run off the event loop under the transcript lock; peer post admission and cost settlement wait for it outside the loop and re-check membership and pause under it.
- Email is multi-account (N accounts, any IMAP/Gmail mix; `email.accounts` in `config.yaml`, id = slug of address). The `email` tool's `account` param selects by address/id; per-account creds from `.env` (`EMAIL__<ID>__PASSWORD`, shared `GMAIL_CLIENT_*`) + `secrets/gmail_tokens/<id>.json` at call time; nothing polls the inbox.

installed product's version and documented host behavior before recommending a feature;
the daemon and the two clients advance their versions independently. Roadmap maintenance
alone changes no runtime contract and needs no product version bump.
