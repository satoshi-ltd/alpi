UI-EXPORT.PAGES · An exported PDF has a header and a page number on every page01

Proposals · ui-export.pages · an exported pdf has a header and a page number on every page
UI-EXPORT.PAGES · desktop · PDF export
An exported PDF has a header and a page number on every pageToday the PDF carries one meta line above the title on page 1 and one footer after the last block, so a loose page 2 does not say whose report it is, and nothing numbers the pages. A header cannot be done in CSS here: a WKWebView print operation on macOS (the engine behind the desktop print sheet) repeats neither a thead nor a position: fixed element, which both print on page 1 only, and WebKit has no page-margin boxes or page counters. The proposal builds the pages itself. The hidden print root measures every block (a paragraph, a list item, a table row, a chart, a code line group), packs them into fixed-height pages and gives each page its own running header (mark, profile, server, title) and footer (profile, date, page n / m). A block taller than a page splits by code line or table row. The phone keeps today's single footer: expo-print has no measured layout before it prints, so it needs a device check first.

A pure paginate(heights, pageHeight) in common/messageExport.mjs packs measured block heights into pages, never splits a chart or a table row, splits an over-tall code block by line, and is covered by unit tests; every page of exportArticle carries the header and the footer with its number and the total; the single end-of-document footer goes away on desktop; the page size follows the print sheet's paper (A4 or Letter) with the margins of today; the Markdown export is unchanged. A creator verify task checks the printed PDF on macOS: header and footer on pages 2 and later, no block cut across pages.

UI-PROFILE.FALLBACKS · Fallback models are set and ordered from the apps02

Proposals · ui-profile.fallbacks · fallback models are set and ordered from the apps
UI-PROFILE.FALLBACKS · mobile · desktop · Profile settings · model
Fallback models are set and ordered from the appsA profile can list fallback_models, tried in order when the main model's provider fails, but only alpi setup edits them: the apps do not show that fallbacks exist, host.profile.detail does not return them, and host.config.set_field would store a list as a string. A profile on one provider has no cover for an outage unless its owner knows to open the console. The proposal adds one Fallbacks row under the helper models: the ordered list with Add and reorder, and one line on when it is used. The rest of the model section stays as it ships.
